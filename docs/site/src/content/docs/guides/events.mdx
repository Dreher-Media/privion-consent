The engine emits five events. Subscribe with `consent.on(event, handler)`; the call returns an unsubscribe function.

## Events

| Event         | Fires when                                                   | Followed by                  |
| ------------- | ------------------------------------------------------------ | ---------------------------- |
| `ready`       | Initial state load completes (defaults **or** hydrated from storage). Replayed to handlers that subscribe later — see below. | —                            |
| `update`      | Any `setCategory` / `setMany` that actually changes state.   | `accept_all` / `reject_all` if triggered from there |
| `accept_all`  | `consent.acceptAll()` runs.                                  | —                            |
| `reject_all`  | `consent.rejectAll()` runs.                                  | —                            |
| `reset`       | `consent.reset()` runs.                                      | —                            |

All handlers receive a single argument: the **current** `ConsentState` (an immutable snapshot of `state` at emit time).

## Ordering

```text
                          ┌─── update ←──── setCategory / setMany
                          │
 construct ──▶ ready ─────┤
                          │
                          ├── update + accept_all  (acceptAll())
                          ├── update + reject_all  (rejectAll())
                          └── reset                 (reset() — does NOT emit update)
```

<Aside title="`update` fires *before* `accept_all` / `reject_all`">
  Inside `acceptAll()` / `rejectAll()` the engine first emits `update` (so generic listeners see the change) and then emits `accept_all` / `reject_all` (so banner-specific listeners can hide the modal, log analytics, etc.). Both events carry the same final state.
</Aside>

## Source semantics

The `source` field on the emitted state reflects the value **at emit time** — the engine no longer mutates `state.source` after emitting. This was a real bug in 0.x (`update` would carry `source: 'api'` while the engine immediately overwrote it to `'banner'`). Listeners can rely on `source` matching the intent of the change.

```ts
consent.on('update', (state) => {
  state.source; // 'banner' | 'preferences' | 'api' — definitively
});
```

<TabItem label="React">

The `useConsent()` hook re-renders the component on every `update` automatically. For one-off side effects (analytics tracking, logging), subscribe directly from a `useEffect`:

```tsx
import { useConsent } from '@privion-consent/react';
import { useEffect } from 'react';

function ConsentLogger() {
  const { consent } = useConsent();

  useEffect(() => {
    const off = consent.on('update', (state) => {
      analytics.track('consent_changed', state);
    });
    return off;
  }, [consent]);

  return null;
}
```

</TabItem>
<TabItem label="Astro">

The engine instance is attached to `window.__privionConsent` by `<PrivionScript>`, which then announces it with a `privion:ready` CustomEvent on `window`. Because Astro bundles `<script>` tags as separate modules with no ordering guarantee, check the global first and fall back to the event — no polling needed:

```astro
<script>
  function withConsent(cb) {
    if (window.__privionConsent) return cb(window.__privionConsent);
    window.addEventListener('privion:ready', (e) => cb(e.detail.consent), { once: true });
  }
  withConsent((consent) => {
    consent.on('ready', (state) => {
      console.log('initial state (incl. stored consent)', state);
    });
    consent.on('update', (state) => {
      console.log('state changed', state);
    });
  });
</script>
```

## `ready` replays to late subscribers

`ready` first fires **synchronously inside the constructor**, *before* `new PrivionConsent(...)` returns — so no consumer can be subscribed at that moment. To make the initial load observable anyway, the engine **replays** `ready` to every handler that subscribes after initialization: the handler is invoked immediately (synchronously, before `on` returns) with the current state, exactly once.

This matters most for **returning visitors**. Consent restored from storage is not a state *change*, so it never fires `update` — `ready` is the only event that carries a hydrated prior decision. A subscriber that grabs the engine from `window.__privionConsent` long after boot still learns the stored consent without polling `getState()`:

```ts
consent.on('ready', (state) => {
  // Runs immediately if the engine already initialized — including when
  // `state` was hydrated from a prior session's stored consent.
  if (state.categories.analytics === 'granted') initAnalytics();
});
consent.on('update', (state) => {
  // Live changes from this session's banner/preferences.
});
```

If you only need the snapshot and no callback wiring, `consent.getState()` after construction returns the same state `ready` emits.

<Aside title="Before core 1.1">
  Older engines did not replay `ready`; a handler subscribed after construction never fired, and hydrated consent was only reachable by polling `getState()`. If you carry a bounded-poll workaround from that era, you can delete it once you're on a replaying core.
</Aside>

## Error handling

Errors thrown from a handler are caught by the engine and reported via `console.error` so one bad listener can't break another or block subsequent events. If you want app-level visibility, wrap the React tree in [`<ConsentErrorBoundary>`](/reference/api/#consenterrorboundary) for render-time errors, and use `onSyncError` for backend-sync errors specifically.

## What's *not* an event

A few things people sometimes assume are events but aren't:

- **Page navigation.** The engine is unaware of route changes. SPAs that re-mount the consent provider on route change should call `dom.destroy()` on the old `PrivionDomHandle` before constructing a new one — otherwise the old MutationObservers keep firing.
- **Storage external changes.** If another tab clears `localStorage` / cookies, the engine doesn't know. This is consistent with most consent libraries; cross-tab sync isn't in scope for v1.
- **Region resolution.** `region` is read once at construction. Re-resolving for a new region needs a new engine instance.
